Session固定攻击

Created2026-08-08|Updated2026-08-08|学习日志
|Post Views:

打开题目，页面上写着两行关键信息：

  • 默认账号密码是 test/test
  • Flag 在管理员页面里

还看到一个「Send Message to Admin」的链接——可以给管理员发消息。

第一步：登录测试账号

我先用 test/test 登录，进去后显示：

我不是管理员，看不到 flag。点进 /message，看到一个表单：

  • msg：消息内容
  • sessionid：我的 session ID

第二步：理解 Session（会话）是什么

登录网站后，服务器会给我发一个”通行证”——Session ID。之后我每次访问页面，浏览器自动带上这个通行证，服务器就知道”哦这是那个 test 用户”。

这个通行证长这样（一串随机字符）：

按 F12 → Application → Cookies，就能看到 session 的 Value，这就是你的 Session ID。

关键点：谁拿着这个通行证，谁就是 test 用户。

第三步：发现可疑的 sessionid 参数

发消息的表单里有个 sessionid 字段，提示写着”Your session id”。

我仔细一想：这个字段把我的 session ID 发给了管理员。如果管理员 bot 用了我指定的 session ID 去访问网站……那管理员登录后的身份，不就跟我的 session ID 绑在一起了？

这就是**会话固定（Session Fixation）**漏洞的核心思路：

第四步：发动攻击

我在 /message 表单填入：

字段 值
msg 随便写个 hello
sessionid 我自己的 session ID（从 Cookie 里复制的）

提交后显示：Message sent to admin!

第五步：刷新页面，我就是管理员

回到首页刷新：

页面变成了 Welcome admin，flag 直接出现在页面上！

🎉 Flag

攻击流程图解

总结

  1. Session Fixation 的本质：攻击者先拿到一个 session ID，然后让受害者使用同一个 session ID。受害者登录后，这个 session 就有了受害者的权限，攻击者就能以受害者身份访问网站。

  2. 防御方法：

    • 用户登录成功后，立即重新生成一个新的 session ID（session_regenerate_id()）
    • 不要让用户自己指定 session ID
    • 把 session cookie 设为 HttpOnly 和 Secure
    • 在 session 中记录 IP 或 User-Agent，发现不一致就作废

  3. 这道题的漏洞：消息表单里的 sessionid 参数允许攻击者向管理员传递任意 session ID，而管理员 bot 在访问时没有重置 session，导致攻击者的 session 被”升级”为管理员权限。

一些问题

Q1：什么是 Session ID？我怎么知道自己的 Session ID 是什么？

Session ID 是网站发给你的”通行证编号”——登录后用来证明你就是你。打个比方：你去游泳馆，前台登记后给你一个手牌（柜子号码），你每次进出刷一下手牌，系统就知道”哦，这是 3 号柜的客人”。Session ID 就是这个手牌。

在浏览器里按 F12 → Application → Cookies → 找到 session 那一行，Value 就是你的 Session ID。

Q2：为什么回首页刷新就变成管理员界面了？

因为管理员 bot 用你给的 session ID 登录后，服务器的记录被改了：原来 session=A → test，管理员登录后变成 session=A → admin。服务器的”签到表”上，你的 session 对应的用户名从 test 被覆盖成了 admin。你再拿着同一个 session ID 回去，服务器查表说你等于 admin，就把管理员页面（含 flag）返回给你了。

Q3：为什么我发给 bot 的 session ID，它就用了？

这是题目故意设计的漏洞。正常应该在登录后重新生成一个 session ID，但管理员 bot 直接把你表单里填的 sessionid 拿来自己用了——这就让你的 session 被”升级”成了管理员权限。

打个比方：银行柜员拿了你给的排队号去登录系统做事，你再拿着同一个号就变成柜员了。

Q4：管理员 bot 是怎么处理消息的？

管理员 bot 其实就是一个自动化的浏览器程序，大概长这样（伪代码）：

bot 拿到你表单里填的 sessionid 值，直接把它设成了自己的 cookie。正常的 bot 应该用管理员自己的 session 去登录，而不是用发件人提供的 session。这就是漏洞根源。
